# 未知迷宫中电脑鼠探索算法的比较与分析

Computational Thinking for AI 小组项目｜建议选用 Track A：自主机器人导航与算法分析。

本项目用 **Python 仿真比较多种迷宫探索与路径规划算法，支持组员提出、实现和验证自己的新策略**。电脑鼠开始不知道完整地图，只能逐步探测墙壁、更新地图、选择下一步，最终到达目标。无需实体机器人。可以分析已有算法、改进已有方法，或设计自己的算法；创新不是强制门槛，性能提升也不是预设结论。

**当前状态：环境与接口（A1/A2）、地图（A3，现共 394 张比赛迷宫 + 120 张计划生成地图）、9 个算法（B1–B3、C3）、可视化上位机（`tools/MazesTest`）、实验计划与正式批量实验（D1/D2，结果在 `results/standard/`）和运行演示说明（D3）已完成；自主设计的新方案（C1/C2）与最终报告（`Docs/Result.md` 中文初稿，第 2 章待用正式结果更新）进行中。**

## 研究问题与范围

> 在相同迷宫、初始信息、观测能力和预算下，不同探索算法及本组设计的策略，在到达效率、重复移动与计算开销上有什么差异？为什么？

| 类别 | 可认领算法／策略 | 实现与比较重点 |
| --- | --- | --- |
| 未知迷宫基线 | 沿墙法（左手／右手） | 简单局部策略，记录环路和内部目标下的失败，不假定总能到达 |
| 未知迷宫探索 | DFS＋回溯 | 访问标记、固定方向顺序、实际移动回溯、累计成本 |
| 未知迷宫探索 | Flood-Fill | 距离传播、在线地图更新、未知边假设与方向选择 |
| 未知迷宫重规划 | 重复 A* | 在当前已知／乐观地图上规划，观测新墙后重算；明确无路时的处理 |
| 未知迷宫探索 | 前沿探索策略 | 选取与未知区域相邻的可达前沿，用已知通路导航；比较目标距离与信息收益 |
| 本组创新 | 自创算法、混合策略或已有算法改进 | 提出规则、伪代码、复杂度、与现有方法的关系，并通过实验验证 |
| 已知地图规划（单独实验） | BFS、Dijkstra、A* 等 | 地图相同且完整时比较最短路与计算成本；转弯代价实验需统一状态与代价 |

候选列表不封闭，也不要求全部实现。建议先确定统一接口、完成两个可靠基线，再按成员能力选取更多算法，最终建议覆盖 3–5 个有明确差异的策略；这是工作量建议，不是课程硬性数量要求。

Flood-Fill 的距离传播可以用 BFS 实现，因此不把“BFS”和“Flood-Fill”仅按名称当成独立方案。未知迷宫比较的是**完整的探索策略**；已知地图最短路是另一组实验，不能将两者混成同一个效率排行榜。每个算法在运行前登记信息假设、方向选择规则、失败条件及是否含随机性。

### 可以自己创造算法吗？

可以，支持作为独立任务认领。可以提出新动作选择规则、前沿评分、循环规避机制、增量距离更新或混合策略，也可以尝试更独立的设计。举例：把目标距离、预计转弯、重复访问和信息收益组合成前沿评分，再在已知可达区域中规划到选中的前沿。这是**待验证的设计思路**，不是已证实的新算法或更优结论。

自创／改进方案需交付：设计动机、状态与输入、完整决策／回退／终止规则、伪代码、复杂度、Python 实现、基线对比和消融实验（逐项移除新增机制）。用开发地图调参、冻结参数后在独立测试地图评价；报告失败案例、额外成本与不提升的结果。引用借鉴的方法，在完成文献核查前称为“本组提出的策略／变体”，不宣称全球首创。

基础范围不含实体小车、PID、定位误差、动态障碍和竞速控制。算法数量可扩展，但优先保证实验公平、分析深入和可复现性。采用自创方法仍可属于 Track A 的算法设计与评估；若转向独立研究型 Track B，再按 brief 补充文献综述与批判性分析。可选的扩展方向见下方“扩展规划”。

### 分层结构：本项目目前只研究“决策层”

真实机器人（例如课程作业中的仓库无人机）通常分三层；本项目有意只建模决策层，以便把结果差异归因于探索策略本身（控制变量）。

| 层 | 真实电脑鼠中的内容 | 本项目现状 | 可选扩展 |
| --- | --- | --- | --- |
| 决策层 | 选择下一步往哪走 | `src/` 中的各策略 | 新算法（见下表） |
| 感知层 | 红外传感器读数融合，判断有无墙 | 理想观测：每格四向墙壁 100% 准确 | **E2**：传感器噪声＋置信度融合 |
| 控制层 | 电机加减速、转弯控制 | 走一格 = 1 步，转 90° = 1 次 | **E1**：运动时间模型 |

```text
决策层  src/dfs.py、src/flood_fill.py …（尽量不改）
   ↑ Observation          ↓ 方向
感知层  可选包装：噪声传感器 + 置信度融合（E2）
   ↑ 真值墙壁             ↓ 方向
控制层  可选包装：运动时间模型（E1）
   ↑                      ↓
环境    src/environment.py（不修改）
```

设计原则：两层都以**可选包装层**实现，默认关闭，不修改 `src/environment.py` 和现有策略。

- **E1 控制层（建议先做，不改接口）**：根据实际路径和朝向计算运动时间，直线采用梯形速度曲线（越长越快），转弯有固定耗时，参数参考真实电脑鼠并记录来源。新增“预计用时”指标；按时间排名可能与按步数不同。该模型也可为转弯加权算法的 λ 提供依据。
- **E2 感知层（需先开 Issue 讨论）**：传感器按方向设定准确率（例如前方 0.95、侧方 0.80、后方不可见）。每面墙维护对数几率置信分数 S，观测“有墙”加 w、观测“无墙”减 w，其中 w = ln(p/(1−p))，即准确率越高权重越大（与按 1/σ² 加权的传感器融合同理）；P(有墙) = 1/(1+e^(−S))。
  - **接口变化**：现在撞墙记为 `invalid_action` 并结束运行；有噪声时应改为“撞墙 = 一次准确观测、原地不动”。这会改变公共规则，须先在 Issue 中达成一致，并同步修改 `src/README.md`。
  - 噪声带有随机性，每个设置需用多个种子重复，报告均值与离散程度。
- **不做**（写入报告的局限分析）：定位误差（属于 SLAM 问题，超出课程范围）、电机 PID（偏离课程主题）。

### 候选新算法

| 算法 | 要回答的问题 | 难度 | 建议任务 |
| --- | --- | --- | --- |
| 沿墙法（左手 / 右手） | 反面基线：中央目标和环路下为何失败、何时成功 | 低 | B3（已完成） |
| 前沿探索 | 总是前往最近的“已知与未知区域交界处”，目标从“到达终点”变为“摸清地图”，比较两种目标下的行为 | 中 | E3（扩展） |
| 转弯加权 Flood-Fill | 状态扩展为（格子, 朝向），代价 = 步数 + λ×转弯，在其上运行 Dijkstra；改变 λ 画出步数与转弯的权衡曲线 | 中 | E3（扩展） |
| 增量重算（D* Lite 等） | 与全量 BFS 重算相比，路线可能相同但计算量不同：区分移动成本与计算成本 | 中高 | E3（扩展） |
| 死路剪枝 | 三面是墙的格子及其向外传递的死胡同不再进入，能减少多少重复访问 | 低 | C1 / C2 |
| 结构先验 | 利用比赛迷宫规律（目标区只有一个入口、除目标区外无 2×2 空地）剪枝；在比赛迷宫上省多少、在随机迷宫上是否吃亏 | 中 | C1 / C2 |
| 加权评分＋元启发式调参 | 评分 = w₁·目标距离 + w₂·转弯 + w₃·重复访问 − w₄·信息收益；“权重 → 平均步数”呈台阶状、不可微、多局部最优，用随机搜索或模拟退火在开发地图上调参，冻结后在测试地图上评估 | 中 | C1 / C2 |
| 已知地图最短路（参照） | 不参与排名，作为全知最优解：报告“探索步数 ÷ 最短路长度” | 低 | C3 |

不推荐强化学习：需要在同一张地图上反复训练，等同于泄露地图信息，与未知迷宫的前提冲突（可写入局限分析）。

### 研究方向（实验设计）

| 方向 | 内容 | 建议任务 |
| --- | --- | --- |
| 两阶段规则（探索＋冲刺） | 按真实比赛规则，先探索再从起点冲刺。未知边全部视为通路与全部视为墙时的两个最短路长度相等，即证明已知路线最优，此时可停止探索。比较“探索成本 + 冲刺成本”，排名可能与只看到达步数时不同 | D5 |
| 迷宫难度刻画 | 定义环路比例、死胡同比例、分岔数、“欺骗度”（乐观假设被新墙推翻的程度）等特征，分析与各算法表现的关系 | D4 |
| 对抗式生成最坏迷宫 | 用模拟退火在保持目标可达的前提下加墙或拆墙，最大化某算法的“步数 ÷ 最短路长度”，得到最坏情况样本 | D4 |
| 控制变量实验 | 用上位机的生成器（记录种子）固定尺寸，改变环路比例（例如 0%、10%、30%），每组几十张地图，观察各算法差距如何变化 | D2 |
| 计算复杂度实测 | 在 8×8、16×16、32×32 上测每步计算时间，对照理论复杂度（如全量重算 O(格子数)） | D2 |

**建议主线：“乐观假设的代价”**：Flood-Fill 依赖“未知边可通行”的乐观假设。它什么时候会被误导（难度刻画、对抗迷宫）？怎样降低被误导的代价（死路剪枝、结构先验、加权评分）？换成两阶段规则后结论是否仍然成立？用一条主线串起算法与实验，避免罗列结果。

### 与现实的对应（用于报告的问题定义和局限分析）

扫地机器人首次进入新户型（覆盖与重复访问）、仓库机器人或无人机遇到新障碍后改道（重新规划）、搜救机器人在未知废墟中寻找目标、火星车移动代价远高于计算代价、电脑鼠比赛（两阶段规则）。仿真与现实的主要差距包括理想观测、统一步长代价、四向观测、已知自身位置和不限电量；可以挑选一到两项放宽（E1、E2 或有限视野），其余写入局限分析。

上表中的 D* Lite、两阶段规则、死路填充等均为已有方法；本组的贡献在于把它们放进统一框架进行比较与分析，在完成文献核查前不宣称首创。

## 基础实验约定（实现前共同确认并记录变更）

- 建议主测试集采用 16×16 网格，起点在角落，目标为中央 2×2 区域；小地图用于调试。具体坐标、起始朝向与地图格式由 A1 固定。
- 真值地图只交给环境。所有未知迷宫策略从同样的未知地图开始，每次在当前格子获得四向墙壁观测。这是本项目的理想观测假设，不是实际传感器模型。
- 一次跨相邻格子的合法移动算一步；转向独立计数（180° 算两次 90°）。DFS 回溯必须真实移动并计步，不能瞬移。
- Flood-Fill 初始将未知内部边暂作可通行，外边界为墙；观测墙壁时双向同步更新。基础实现先采用全量 BFS 距离重算。
- 建议 DFS 按北、东、南、西选未访问邻格；Flood-Fill 先选距离最小邻格，同值时依次优先未访问、直行、北东南西。距离不可达时明确处理，不无限循环。
- 建议统一移动预算 `20 × 格子数`、计算预算 30 秒/次；实验前共同确认，所有策略相同。到达任一目标格即停止；已知地图实验另行登记相同规则。超时/超步记录为“预算内未到达”，不等同于证明无解。
- 每种算法新增时复用相同环境接口和指标，记录算法名、配置与版本。新策略与调参方法将开发地图和最终测试地图分开，测试前冻结参数。
- 先用少量人工地图验证，再收集不少于 20 张有代表性的测试地图；注明来源、改动、起终点及地图 ID。随机生成地图须记录种子。
- 原始步数结果保持可复现；关闭动画后重复计时，记录机器、Python 版本和依赖版本。计时包含规划初始化、观测后更新与决策，不含绘图和磁盘读写；计时和峰值内存可分轮测量以避免干扰。

| 指标 | 统计口径 |
| --- | --- |
| 预算内到达率 | 成功到达次数 / 总运行次数，失败和原因也保留 |
| 首次到达步数 | 成功运行实际跨格移动次数；失败不以 0 代替 |
| 重复访问次数 | 起点记一次访问；随后每次进入已访问格计一次 |
| 转弯次数 | 累计 90° 等效转向次数 |
| 计算时间 | 明确范围后的总策略计算时间，报告重复测量统计 |
| 峰值内存 | 记录测量工具和范围；例如 tracemalloc 不代表进程全部内存 |

报告中按地图配对展示结果，同时报告失败率，避免只挑成功运行。若统计节点数，必须解释不同算法的“节点操作”是否可比。

## 本地准备

需要 Python 3.10 及以上（代码使用了 `int | None` 等 3.10 起支持的写法）。当前开发、测试和初步实验使用 **Python 3.14.7**；正式实验前全组统一为同一版本，并在结果中记录。安装 Git，克隆后进入仓库；完整协作步骤见 [CONTRIBUTING.md](CONTRIBUTING.md)。

```bash
python -m venv .venv
```

Windows PowerShell 激活：`.venv\Scripts\Activate.ps1`；macOS/Linux：`source .venv/bin/activate`。若无法激活，可直接调用虚拟环境里的 Python。

```bash
python -m pip install -r requirements.txt
```

环境与算法只使用标准库；PySide6 用于可视化上位机，Matplotlib 用于实验统计图（附带的 Pillow 用于导出 GIF）。MMS 单独下载。当前可运行的命令：

```bash
python -m unittest discover -s tests       # 运行全部测试
python tools/MazesTest/maze_app.py         # 打开上位机：实时运行、同屏对比、地图编辑（见 tools/MazesTest/README.md）
```

实验与演示：`python src/run_experiments.py --plan standard`（结果写入 `results/standard/`，规则见 `Docs/experiment-plan.md`）；完整的运行与答辩演示说明见 `Docs/demo-guide.md`。
